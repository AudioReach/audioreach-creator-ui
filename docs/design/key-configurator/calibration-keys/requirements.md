# Calibration Keys (CKV) — Requirements

## Feature Overview and Strategic Fit

Key Configurator is the panel used to configure key-based settings for a
project: subgraph key vectors, subsystem keys, calibration key vectors
(CKV), and tag key vectors (TKV) for module instances. It exists to
simplify setting up and maintaining audio use-case configuration without
hand-editing raw project data.

CKV state — which calibration key values are configured for a module
instance, the keys available to configure, and the per-module parameter
(PID) list — is owned by the graph designer's per-project configuration
state (a dedicated CKV slice composed into `GraphDesignerStore`), scoped
per open project tab, mirroring the migration TKV's design just
established. This is the single supported home for CKV state and behavior
going forward:

1. **Edit functionality** — the CKV panel's existing add/edit/delete/
   apply behavior becomes the supported, non-regressed baseline.
2. **Per-project scoping** — CKV state is scoped to the project tab it
   belongs to, so multiple open projects never share or overwrite each
   other's CKV state.

## Architectural Impacts

- **Graph Visualization Support** — the Key Configurator panel already
  has access to the per-project configuration state it needs; no
  provider-tree changes are required to support this feature.
- **Scalability** — CKV state is per-project-tab, so opening multiple
  projects simultaneously keeps each project's CKV configuration fully
  independent — no cross-tab overwrite risk.
- **Instance-Level Scoping** — configured calibration key values are
  stored per module instance, keyed by each instance's own unique
  identifier, so multiple placed instances of the same module type never
  share or overwrite each other's configuration.
- **Data ownership, not fetch ownership** — selecting a module instance
  does not trigger a dedicated fetch for CKV data at all. Configured keys
  are read directly from that instance's `ModuleInstance.ckvs`, already
  populated on the per-project graph state by the existing graph-load
  flow; per-module parameter definitions are read from the already-loaded,
  per-tab module-definition state. Both reads happen entirely within the
  per-project configuration state (no dependency on logic outside it —
  see Decision D1), so there is no per-selection fetch left to coordinate.
- **Graph Data as the single saved-state owner** — Graph Data
  (`ModuleInstance.ckvs`) is the only saved source for a module instance's
  configured CKVs. The Key Configurator does not maintain a separate CKV
  data store; add/edit/delete operations write back into Graph Data (see
  requirement 22).

## Assumptions

- **Reset on Use Case Refresh** — the Key Configurator view resets to an
  empty state when the use case is refreshed.
- **Configuration Mode Control** — in Offline mode, key configuration is
  only permitted when graph modification (edit mode) is enabled; in RTC
  mode the panel is always read-only.
- **D1 — Self-contained read.** Reading and populating CKV data for a
  selected module instance is handled entirely by reading already-loaded
  per-project graph and module-definition state, with no dependency on
  fetch/distribution logic that lives outside the CKV slice, and no
  dedicated network request of its own.
- **D3 — Slice `get()` access.** The CKV slice's creator function gains
  access to the store's `get()` (today it only receives `set()`), needed to
  read `graphData` and the per-tab module-definition list when deriving
  CKV data for a selected instance — mirroring how other
  `GraphDesignerStore` slices are already wired.
- **D4 — Independent context type.** The CKV slice defines its own
  configuration-context type rather than importing the configuration-context
  type already defined inside the `key-configurator` feature — the two
  features cannot import each other, so each owns the shape it needs. The
  widget that has access to both is responsible for translating a selected
  configuration item into the shape the CKV slice expects.
- Key definitions and per-module-type parameter definitions are fetched at
  most once per project tab and reused across module selections within
  that tab, consistent with the "reset on use case refresh" assumption
  above.

## Open Questions

1. **Backend save contract for CKV.** Apply persists configured CKVs into
   Graph Data (`ModuleInstance.ckvs`) immediately — this part is settled
   (requirement 22). What remains open is whether/how Graph Data's CKVs
   are themselves pushed to the backend beyond that: no endpoint
   currently exists for CKV list-management (only parameter-_value_
   endpoints exist, covering a different operation). Should this be a
   single bulk endpoint covering all modified modules/instances in one
   request, or a per-module (or per-instance) endpoint once per changed
   module? This mirrors TKV's identical open question and may share a
   single resolution across both features — needs clarification before
   design can finalize the save flow.
2. **New-entry `systemId` shape.** `CkvDto.systemId` is non-optional, so an
   existing, backend-loaded entry always carries its identity already — not
   a concern. The open gap is a CKV entry created through Add: it has no
   backend-assigned identity until it's actually saved, so something must
   be assigned locally in the meantime. The same deterministic-composite
   approach proposed for TKV (derived from the sorted `systemId`s of the
   entry's selected key/value pairs) is the natural candidate here too, but
   needs the same sign-off before implementation, and may share a single
   resolution with TKV's identical question.
