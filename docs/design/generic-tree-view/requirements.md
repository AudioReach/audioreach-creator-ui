# Generic Tree View/Module Data Tab (Calibration Window) — Requirements

> Design: [design.md](design.md)

---

## Overview

The Generic Tree View is a data editor for hierarchical parameters in
the AudioReach Creator application. It is used to inspect and tune the
parameters of an SPF module after double-clicking it on the graph
designer canvas, and to edit relevant subgraph properties from a
properties panel.

It accepts a hierarchical parameter tree adapted from the backend DTOs,
renders each parameter's elements as typed input controls, and tracks
which values have been modified relative to the last committed
snapshot. The host widget owns the Get (re-fetch from the backend) and
Set (write changes to the backend) operations; this component surfaces
the dirty items on demand and re-seeds itself when a new snapshot
arrives.

It is composed by a host widget (the Module Data Tab, or a domain-specific
equivalent) that is responsible for fetching data, persisting session
state across tab switches, and wiring the feature to the store. The
feature itself is store-agnostic.

**Key design principles:**

- The parameter and element tree structure is entirely DTO-driven — the backend
  controls what controls are rendered.
- All editing state is persisted in the store so that switching tabs does not lose unsaved edits, selections, or view mode.
- The feature must remain agnostic to the business domain (modules, CKV indices,
  projects) so that future widgets (tag-data, subgraph properties) can reuse it
  without modification. It uses `AnyElementDto` from `entities/spf-module-data`
  as the shared element rendering contract — this is a UI rendering type, not
  business domain coupling.
- Improve upon the single tree view structure that the current WPF control uses to make
  view/edit of parameters and elements easy.

### 1.6 State Management

| ID       | Requirement                                                                                                                                                                                                                                                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| FR‑ST‑01 | The feature shall maintain a flat map of current element values addressed by element path. The parameter tree passed in by the caller shall never be mutated.                                                                                                                                                                                                            |
| FR‑ST‑02 | A committed snapshot of element values shall be maintained at the last successful Get or Set. Dirty status of each element shall be computed by comparing its current value against this snapshot.                                                                                                                                                                       |
| FR‑ST‑03 | Every element in the tree shall be uniquely addressable by a path derived from its parameter ID and structural position. This path is the single key used across all state tracking (current values, committed snapshot, dirty state, array counts).                                                                                                                     |
| FR‑ST‑04 | Dirty state and set state shall be mutually exclusive per element: when an element re-enters dirty state it shall no longer be considered set, and this transition shall be atomic.                                                                                                                                                                                      |
| FR‑ST‑05 | When the caller supplies a new parameter tree (a new `data` prop reference after mount), the feature shall re-seed element values, committed values, and array counts from the new tree, and clear dirty, set, and invalid tracking. `initialUiState` is consumed on mount only; subsequent `data` prop reference changes always trigger full re-seeding of edit state regardless. |
| FR‑ST‑06 | All UI-preference and edit-session state (selections, expansions, view mode, element values, dirty tracking, split position, policy filter) shall be persisted to the caller's store. The feature shall accept an initial session snapshot on mount and shall emit changes back so the caller can keep the snapshot up to date.                                          |
| FR‑ST‑07 | When an initial session snapshot is provided on mount, the feature shall restore the exact session it represents — including unsaved edits, selections, and view mode — without any network call. This is the mechanism that preserves full session state across tab switches.                                                                                           |
| FR‑ST‑08 | When no session snapshot is provided (first load of a new module), the feature shall initialise the policy filter to show **Basic** elements only (the consumer may provide an alternative initial filter via a prop — see the design document). The view mode shall default to **Modern**.                                                                              |

### 1.7 Get / Set Lifecycle

Set and Get are host-widget responsibilities. The feature holds working
state and reports it on demand; the widget dispatches to the backend and
feeds the result back in.

| ID       | Requirement                                                                                                                                                                                                                                                                                                                            |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR‑GS‑01 | The feature shall not send anything to the backend, either for Set or for Get. It shall make its current dirty items available to the host widget on demand; the widget shall dispatch the write.                                                                                                                                      |
| FR‑GS‑02 | On a successful write, the widget shall obtain the updated parameter tree from the backend and hand it back to the feature as the new snapshot. The feature shall re-seed all state from that snapshot and clear dirty, set, and validation tracking — the same pathway as any other externally-driven snapshot change (FR‑ST‑05).     |
| FR‑GS‑03 | On a failed write, the widget shall not hand a new snapshot to the feature. The feature shall therefore preserve unsaved edits, dirty markers, and validation errors automatically. The widget shall be responsible for surfacing the error to the user.                                                                               |
| FR‑GS‑04 | Get shall re-fetch the current parameter tree from the backend and hand it to the feature as a new snapshot, using the same success / failure pathway as Set (FR‑GS‑02, FR‑GS‑03). The feature shall not orchestrate the fetch.                                                                                                        |
| FR‑GS‑05 | The feature shall expose a way to synchronously return the items that have unsaved edits (with their current element values), or a null-equivalent when nothing is dirty. This is used by widgets with a manual Set button and by bulk save-all flows. The widget is responsible for constructing the domain-specific request payload. |
| FR‑GS‑06 | The feature shall expose a way to synchronously return the complete current parameter tree as last known to it (the most recent snapshot the caller handed in). This is used when a caller needs a full snapshot — e.g. for Batch Copy — without a server round-trip.                                                                  |
| FR‑GS‑07 | The feature shall expose a way to programmatically discard unsaved edits — a local rollback that re-seeds state from the current snapshot and clears dirty and set tracking. This shall not trigger any backend fetch.                                                                                                                 |

| FR‑EH‑06 | `min`/`max` bounds are absent on many elements. Validation shall be silently skipped when either bound is undefined — the input shall never show an error for an unconstrained element.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

### 1.13 Auto-Commit Mode

Auto-commit mode enables the feature to hand dirty items to the host
widget as soon as the user finishes editing a field, without requiring
a Set button. It is appropriate for lightweight panels (e.g. subgraph
properties) where seamless inline editing is desired.

The trigger for a commit is **loss of focus (blur) on a leaf input
control**, or the equivalent atomic-commit event for controls without a
text field:

- Text-input controls (hex, Q-format, dB, string) — commit on blur.
- Dropdown / bit-field-sub-field controls — commit on option
  selection; the dropdown closes and returns focus in one gesture,
  which is functionally equivalent to blur.
- Switch controls (boolean synonym pair) — commit on toggle; a switch
  is atomic and has no separate "finished editing" state.

No timer is involved. Rapid keystrokes within a single field never
commit mid-value.

| ID       | Requirement                                                                                                                                                                                                                                                                                     |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR‑AC‑01 | When auto-commit mode is enabled, the feature shall emit the current dirty items to the host widget on the blur or atomic-commit event of a leaf input control, provided there are unsaved edits and no elements are in invalid state. No manual Set affordance is provided within the feature. |
| FR‑AC‑02 | Dirty indicators shall remain visible after a commit is emitted so the user can see which values are in flight until the widget's write completes and a new parameter tree flows in (per FR‑GS‑02).                                                                                             |
| FR‑AC‑03 | If the widget's write fails (per FR‑GS‑03), no new parameter tree flows in and dirty markers remain. The widget shall surface the error. The next successful commit trigger shall emit again.                                                                                                   |
| FR‑AC‑04 | Auto-commit mode and read-only mode are mutually exclusive. If both are specified, the feature shall behave as read-only (no edits, no commits).                                                                                                                                                |
| FR‑AC‑05 | Range validation (§1.12) shall still apply in auto-commit mode. If the departing field is invalid, no commit shall be emitted — the user must correct the value before the next commit opportunity.                                                                                             |

### 1.15 Module Enable Switch

A per-module switch overlay on the canvas node reflects the current

| ID        | Requirement                                                                                                                                                                                                                                                                                                                                              |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR‑MES‑01 | Every module whose backend-supplied module definition declares `PARAM_ID_MODULE_ENABLE` shall render a switch overlay on its canvas node. Presence shall be determined synchronously from information already available at project load — no additional network call. | FR‑MES‑02 | The switch shall render in one of three states: (State 1) a real toggleable switch when the module's active CKV is resolved and the enable value is known; (State 2) a non-interactive loading placeholder when the CKV is resolved but the enable value has not yet been fetched; (State 3) hidden entirely when no CKV can be resolved for the module. |

The commit shall write only the enable parameter (not the module's full parameter tree).                                                                                                                                                |

### 1.16 Subgraph CKV Header

Every subgraph node in the use case visualizer canvas renders a header
overlay containing one selector per unique CKV key across the modules
in that subgraph. This header owns the active CKV selection for every
module in the subgraph. The full design is in the design document.

| ID        | Requirement                                                                                                                                                                                                                                                                                          |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR‑SGH‑01 | Every subgraph node shall render a header overlay containing one selector per unique CKV key across every module's CKV list within that subgraph.                                                                                                                                                    |
| FR‑SGH‑02 | Each selector's option list shall be the sorted union of values seen for that key across the subgraph's CKVs (WPF parity).                                                                                                                                                                           |
| FR‑SGH‑03 | If the subgraph's CKVs are correlated — i.e. the number of theoretically-possible key/value tuples exceeds the number of CKVs actually present — the sentinel value `NA` shall be injected as an additional option in every selector. This matches the WPF app's handling of the same case.          |
| FR‑SGH‑04 | On mount, each selector shall default to the first value in its sorted option list (WPF parity). In dependent-CKV subgraphs this may leave some modules in an unresolved-CKV state on first paint — this is the deliberate behaviour of the initial release; a smarter default is deferred (see §4). |
| FR‑SGH‑05 | Selection changes shall not cross-filter other selectors. Tuples that do not resolve to a real CKV for a given module shall leave that module in an unresolved-CKV state (see FR‑MES‑07). Cross-filtering is deferred (see §4).                                                                      |
| FR‑SGH‑06 | The subgraph header selection shall be persisted in the graph designer's store as the single source of truth for header selections. Every module in the subgraph shall derive its active CKV from that selection; there shall be no separate copy of a module's active CKV maintained elsewhere.     |

### 1.17 Store Lifecycle

Subgraphs are project-scoped entities: a subgraph (identified by
its ID) is defined once, with a specific module set, module `ckvs`
lists, and inter-module links. Use cases are collections of
subgraphs — the same subgraph may appear in multiple use cases. A
use-case switch therefore changes only which subgraph IDs are
currently rendered on the canvas; the subgraphs themselves are
unchanged.

This structure allows cached state (module data, header selections,
UI session state) to survive a use-case switch whenever the same
subgraph is present in both selections. The rules below make that
concrete.

| ID        | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR‑MDL‑01 | Closing a module data tab (per FR‑MDT‑10) shall not clear the module's entry from the store. Reopening the tab shall reuse the cached parameter trees and UI session state as they were at close. (Unsaved edits are always resolved to Save or Discard by FR‑MDT‑10, so there are none to preserve.)                                                                                                                                                                                                                        |
| FR‑MDL‑02 | On use-case switch, let _survivors_ be the set of subgraph IDs present in both the previous and the new selection. For every survivor subgraph, all of the following shall be preserved verbatim: its header selection, and every module data entry whose module belongs to that subgraph (including the entry's cached parameter trees and UI session state). For every non-survivor subgraph, the corresponding header selection shall be cleared and every module data entry belonging to that subgraph shall be cleared. |
| FR‑MDL‑03 | For a survivor subgraph, no refetch shall be triggered by the use-case switch. Because the subgraph's module set, module CKV lists, and header selection are all preserved, every module's active CKV is unchanged and its cached parameter tree remains valid.                                                                                                                                                                                                                                                              |
| FR‑MDL‑04 | For a subgraph in the new selection that was not in the previous selection, the subgraph header selection shall be initialised per FR‑SGH‑04 (first-value defaults). No module data entries shall exist for that subgraph's modules until a per-module fetch is issued.                                                                                                                                                                                                                                                      |
| FR‑MDL‑05 | On project close, all module data entries and all subgraph header selections shall be cleared.                                                                                                                                                                                                                                                                                                                                                                                                                               |
| FR‑MDL‑06 | When a module is removed from a subgraph in-session (e.g. via canvas edit), the store entry for that module shall be cleared. The rest of the subgraph's state (header selection, other modules' entries) shall be preserved.                                                                                                                                                                                                                                                                                                |

## 2. Invariants

**I1 — Authoritative array count:** The displayed instance count for any `ELEMENT_TEMPLATE_ARRAY` shall always come from the runtime-maintained count, not from the number of instances originally returned by the backend (which is only the initial seed).

**I2 — No mutation of the caller's tree:** The parameter tree handed to the feature by the caller shall never be mutated. All working values are held in mutable working state. The original structure is only re-assembled (with updated values) when constructing the Set payload.

**I3 — Dirty/Set mutual exclusion:** An element shall never be in both dirty and set state simultaneously. Editing an element that is in set state shall atomically remove the set state.

**I4 — Element path uniqueness:** Every element in the tree has a unique address derived from its parameter ID and full structural path. Two elements with the same name at different nesting levels produce distinct addresses.

**I5 — Read-only most-restrictive wins:** A control is editable only when all three read-only sources (caller-supplied read-only mode, parameter-level read-only flag, element-level read-only flag) are false. Any one of them being true disables the control, regardless of the others.

**I6 — Single canonical location for the enable value:** For any given module and any given CKV, the value of `PARAM_ID_MODULE_ENABLE` shall exist in exactly one place in the store — inside that module's fetched calibration data for that CKV. Neither the canvas overlay nor any future observer shall hold a shadow copy. Both surfaces (canvas switch and module data tab) shall read from and write through this single location.

**I7 — Single canonical location for subgraph header selection:** The active CKV selection for any subgraph shall exist in exactly one place in the store. Every module in the subgraph shall derive its active CKV from that selection. There shall be no per-module or project-scoped shadow copy of the active CKV.

## 4. Out of Scope

- **`FORMULA` `displayType`** — elements with this display type will not be rendered as formula controls; they fall through to the default hex input.
- **Policy filter and view-mode preference persistence across sessions** — preferences are per-tab only; persisting them to user settings across app restarts is not planned.
- **`toolPolicy` field on older backend versions** — the policy badge chips (§1.4 FR‑RP‑05) require `toolPolicy` to be present in the REST DTO. This field is absent on older backend versions; no fallback rendering is planned.
- **Element metadata editing** — a variant that lets users edit the properties of elements themselves (as opposed to their values) is not in scope for this component.
- **Cross-filtering of subgraph header selectors** — the header uses free selection with an `NA` fallback per FR‑SGH‑05. Adding a wizard-style cross-filter that recomputes other selectors' options on each selection change is deferred to a later release.
- **Persistence of subgraph header selections across sessions** — the header re-initialises to first-value defaults on each project reopen. Per-project persistence is deferred.
- **Explicit cache size cap on cached full parameter trees** — the survivor rule (§1.17) already bounds the store to the current use case's module count, and typical use cases have module counts well within available memory. An LRU cap and demotion mechanism for cached full parameter trees is not in the initial release. Add if profiling of real-world long sessions shows memory growth becomes a concern.
